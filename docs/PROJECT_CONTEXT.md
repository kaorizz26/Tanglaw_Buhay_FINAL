# Tanglaw-Buhay project context

## Purpose and boundaries

Tanglaw-Buhay is a BSIT capstone decision-support system for LGU/CSWDO staff in Pozorrubio, Pangasinan. It uses historical CBMS records to assess household vulnerability and provide separate subsidy pre-screening signals. Its findings are not official poverty classifications, eligibility decisions, approvals, or benefit allocations. A system finding does not create a staff review; staff decisions remain separate from assessments and source records.

Use [AGENTS.md](../AGENTS.md) for permanent development and security rules and [UI_SPEC.md](UI_SPEC.md) for current staff-facing presentation. The [implementation plan](IMPLEMENTATION_PLAN.md) tracks progress. Technical methods, source provenance, assumptions, and detailed limitations remain in the [Developer Guide](../DEVELOPER_GUIDE.md), internal metadata, and capstone methodology. Historical tasks and layouts are not current UI requirements.

## Authorized data and assessment boundaries

- The owner identifies the authorized 2022 Pozorrubio CBMS working dataset as **19,304 households and 69,350 members**. These historical batch counts are not current population estimates. The validated local development source is active batch `1`; designated completed assessment **Run 3** contains its finalized four-program findings. Runs 1 and 2 remain historical records. Run 3 preserves all 16 MPI indicators, scores, ranks, and supporting evidence from Run 2.
- Preserve original responses, blanks, literal `NA`, source field names, survey year, and join identities: household `uuid`; roster member `uuid` plus `line_number`; Section L `section_l_line_number` within the same household. A missing joined record is not automatically a negative response. Use recorded ages for the historical survey period.
- Preserve source and methodological provenance internally, including synthetic E15 support, E01/OFW assumptions, cohort-based attainment approximation, asset crosswalks, food-insecurity handling, and provisional Section L interpretations. The apparent Section L Yes/No recoding is not independently PSA-confirmed. Stored supplemental internet, transportation, and desired-work-hours values remain assessment inputs; never present them as directly collected or verified PSA answers.
- Future Pozorrubio imports are expected to follow the finalized 2022-compatible structure, but each requires validation before activation, preservation of historical batches, batch-specific assessments, and role-based access. Cross-period household progression needs reliable identity matching and is not implemented.

## Existing assessment system

- The adapted MPI has **16 indicators across Education; Health and Nutrition; Housing, Water and Sanitation; and Employment**. Each dimension contributes 25%. Indicator flags are deprived, not deprived, or unknown. Unknowns remain unknown and add zero points without redistributing weight, so scores may understate vulnerability; coverage reports known indicator weight. Exact fractional scores preserve ties, and descending competition ranks belong to the full assessed batch, unchanged by UI filters.
- Four independent subsidy engines produce separate historical findings for **4Ps, SLP, SPISC, and TUPAD**. Their findings do not derive from MPI scores or ranks. `For Review` signals a supported project trigger, `No Historical CBMS Trigger` means relevant historical evidence found no project trigger, and `Needs Data Review` marks missing or conflicting evidence. Supporting context alone is not a trigger; a finding may retain warnings or unverified requirements. These statuses do not establish eligibility or automatically assign staff work.
- The approved TUPAD engine refinement uses only recorded nonwork or irregular work for members aged 18+ with B06=7; missing essential answers remain unresolved. Run 3 adopts these findings; Runs 1 and 2 retain the earlier methodology, including assumed nonwork.
- The approved SLP refinement limits EF (18+, E01=2) and MD (16+, E01=1, E18=3/4/5/6) to B06=7. Recorded nonwork excludes MD; expected E18 skips do not create uncertainty. Run 3 adopts these findings while preserving stored Runs 1/2.
- Finalized mappings, weights, screening rules, uncertainty handling, source evidence, and stored results are protected. Consult `services/vulnerability/`, `services/screening/`, and the [Developer Guide](../DEVELOPER_GUIDE.md) for exact methods; changes require explicit approval.

## Architecture and current functionality

- Flask routes and Jinja2 staff templates use service and PostgreSQL repository layers. Validated imports preserve original source/reference rows, metadata, and historical batches; stored assessment runs and findings are separate from source data. Protected queries read only the selected completed run, currently designated Run 3 for batch `1`, without recalculating results. The Run 3 persistence implementation and focused verification tests are committed. The approved 4Ps presentation refinement is implemented.
- Implemented: database-backed login/logout and session checks; a reusable System Admin guard; controlled backend import and read-only active-batch loading; completed MPI and four subsidy engines; assessment persistence and designated-run selection; protected Household Prioritization with search, filters, pagination, and stored ranks; protected Household Assessment Overview, all 16 MPI indicators with scoped evidence, and Subsidy Screening details; Staff Reviews with initiation, permanent attributed notes, closing recommendations, cancellation, household history, and assessment status summaries (requires migrations 0005 and 0006). Public information pages at `/public` describe four programs without reading CBMS records; they and the public `/test` route retain the development fixture guard. Citizen identity and submissions are not implemented.
- The protected Review Queue shows one current staff review per household/program, using stored municipal ranks and validated filter/return state. Responsible Staff starts as the review creator and can be changed on active reviews with attributed history; both roles retain shared access. Scope selection and date sorting apply across statuses. Migrations 0007 and 0008 are already applied to local development, per owner confirmation. Task 5.2 preserves original closing values and attributed correction/withdrawal history. An effective completed recommendation blocks a repeat Start Review; staff correct or withdraw it instead. Legacy cancellations preserve the latest completed recommendation, while an explicitly withdrawn latest completion never restores an older outcome. Existing active repeats retain their workflow and take precedence in current presentation. The developer-only reset utility backs up and clears disposable review workflow records only after strict local-target checks and interactive confirmation; operational LGU history must never be reset.
- The LGU Staff and System Administrator dashboards show the same historical municipal aggregates from the designated completed run; SPISC counts and linked Prioritization filters use the same current-age logic. Both roles can open the linked assessments and reviews. The Dashboard summary is cached in-process for 30 minutes (keyed by database, batch, designated run, run completion time, Philippine date and barangay; the cache holds 64 entries) and the barangay list for 1 hour per batch; the first Dashboard load after a restart or expiry still takes several seconds (about 6 s for the municipality on the full 19,304-household batch). Data Import remains a protected placeholder. The admin-only Staff Accounts page creates LGU Staff accounts with an editable suggested username, generated initial password shown once, and `must_change_password=true`. Existing accounts default to false. Staff and administrators share `/login`; a flagged account must verify the initial password and set a new one before using protected pages. Password setup clears the flag and revokes older sessions. There is no self-registration. Account listing, edits, deactivation, and password reset remain future work. Household Records provides a read-only, searchable directory with a barangay filter and focused household answers and member roster, linked to the assessment. Remaining workflows include Submissions and the general future-import workflow. See the [implementation plan](IMPLEMENTATION_PLAN.md) for milestone status and dependencies.

## Roles and security

The two approved roles are **System Administrator** and **LGU Staff**. Both roles may access assessment and review routes, initiate subsidy reviews, append notes, finish with a recommendation, or cancel active reviews. Both roles may read Household Records. CBMS imports and staff-account management are admin-only (System Admin only); staff creation is implemented while the remaining web account lifecycle and import controls still need approval and implementation. Imported CBMS records remain read-only to staff. Review actions never alter source records or system findings. Actual CBMS access requires authenticated staff authorization and a protected repository boundary. Private household data, credentials, and household-level comparison exports must not enter Git.
